# План стабилизации и сопровождения

Цель этапа — получить предсказуемый production-продукт, который можно безопасно
обновлять и развивать без ручного расследования каждого сбоя.

## Критерии готовности продукта

- один документированный путь установки, обновления и rollback;
- одна команда запуска всех репозиторных проверок;
- healthcheck проверяет не только процессы, но и свежесть данных и backup;
- схема БД полностью воспроизводится миграциями и проверяется на чистой базе;
- конфигурация валидируется до запуска сервисов;
- критичные расчёты покрыты детерминированными тестами;
- код портала собирается явной композицией без каскада runtime-патчей;
- выпуск версии имеет changelog, commit/tag и короткий smoke-test;
- есть регулярная проверка восстановления из backup и канал уведомлений о сбоях.

## Этап 1 — эксплуатационная достоверность (P0)

- readiness портала возвращает HTTP 503 при недоступной БД;
- healthcheck контролирует последние systemd-результаты, свежесть sync и backup,
  зависшие `RUNNING`, контейнеры, HTTP и диск;
- проверки запускаются через `verify_all.py` в CI и Docker build;
- дублирующий workflow удалён, документация сверена с реальным расписанием.

## Этап 2 — безопасный релиз и восстановление (P0)

- [x] immutable image tag по commit SHA;
- [x] автоматический post-deploy smoke-test и возврат на предыдущий image при ошибке;
- [x] документированный restore drill на отдельной тестовой БД;
- [x] release checklist с проверкой миграций, отчёта и фоновых заданий;
- [x] выполнить первый restore drill на production и зафиксировать результат.

## Этап 3 — управляемая кодовая база (P1)

- единый типизированный слой конфигурации вместо разрозненного чтения env;
- перенос приложения в пакет `arvento_report` без изменения внешних entrypoint;
- замена каскада модулей `*_patch.py` на явную фабрику FastAPI-приложения;
- разделение крупных модулей API, портала и расчётов по ответственности;
- постепенное удаление compatibility-модулей после фиксации контрактов тестами.

## Этап 4 — тестируемая схема и качество (P1)

- pytest как единый test runner, сохранение существующих сценариев;
- интеграционный CI с PostgreSQL/PostGIS и применением миграций с нуля;
- ruff и поэтапная типизация критичных модулей;
- тесты контрактов Excel, API, миграций, очередей и ошибок внешнего API;
- автоматическая проверка зависимостей и плановое обновление lock-файла.

## Этап 5 — наблюдаемость (P1)

- уведомления при ненулевом healthcheck и падении systemd unit;
- структурированные логи с run/job ID;
- метрики длительности pipeline, объёма входных данных, кэша и ошибок;
- политика хранения логов, backup и GPS-партиций с контролем свободного места.

Каждый этап выпускается отдельными небольшими PR. Изменение бизнес-логики
отчётов не совмещается с инфраструктурным рефакторингом.
